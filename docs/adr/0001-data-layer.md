# ADR 0001 — Data layer

- **Status:** Accepted
- **Date:** 2026-10-15
- **Deciders:** project author
- **Context:** Phase 3 — persistence for the 42 progress domain.

## Context

The dashboard models the 42 school experience: campuses, cursus, skills and
projects, students and their enrollments, plus the activity that feeds the
progress timeline (audits, evaluation events, per-day XP snapshots). The API
is async (FastAPI) and PostgreSQL is the store. We need a persistence design
that is idiomatic, testable without a shared database, and honest about the
domain — without over-engineering layers we do not yet need.

## Decision

### 1. Async SQLAlchemy 2.0 with psycopg 3

Use the 2.0 typed ORM (`Mapped[...]` / `mapped_column`) on the async engine
with the `psycopg` (v3) driver. The API is already async; a sync layer would
force thread offloading. psycopg 3 is the modern driver and gives us one
dependency for both the async runtime and synchronous tooling (Alembic
diagnostics, tests).

The engine and session factory are created once in the app `lifespan`, stored
on `app.state`, and disposed on shutdown. `get_session` yields a session per
request.

### 2. Non-native enums with explicit CHECK constraints

Domain enums are `StrEnum` and are **not** stored as native PostgreSQL enums.
Native enums make additions a schema migration and comparisons awkward when
data is generated. Instead each enum column is `VARCHAR` plus a named `CHECK`
constraint, generated from the enum members by a single `_enum_check` helper.

This avoids two traps:

- `Enum(create_constraint=True)` combined with a naming convention makes
  Alembic render the same constraint more than once, producing
  `DuplicateObject` on migration.
- Drift: `alembic check` would not see a native enum's value set changing.

A unit test asserts constraint names are unique within each table.

### 3. Surrogate keys plus natural keys

Every table has a `bigint` `GENERATED BY DEFAULT AS IDENTITY` primary key.
This is stable, compact, and avoids exposing natural identifiers as foreign
keys. Natural identifiers (`users.login`, `cursus.slug`, `campuses.name`) are
kept as unique columns so the API can look entities up by their real-world
handle. Timestamps come from a `TimestampMixin` with server defaults.

Naming of constraints/indexes is fixed by a single `NAMING_CONVENTION` on the
metadata so autogenerated migrations are deterministic.

### 4. Pure domain with infrastructure mappers

The domain is plain frozen dataclasses and `Protocol` repositories
(`StudentRepository`, `AnalyticsRepository`) — no ORM types leak inward.
`infrastructure/mappers.py` converts rows to entities and back. Both concrete
repositories are checked against their Protocols by static typing in a unit
test. We deliberately did **not** add an application/service layer in this
phase: there is no behaviour to orchestrate yet, so it would be speculative.

### 5. Testcontainers and a deterministic seeder

Integration tests run against an ephemeral `postgres:17-alpine` container
started once per session (`testcontainers.community.postgres`). Migrations are
applied once via Alembic with the container URL injected through the config;
each test then runs in a transaction that is rolled back, so tests are isolated
without truncation. Integration tests are deselected by default (`-m "not
integration"`) and run with `just test-integration`.

The seeder (`infrastructure/seed.py`) is deterministic: a `SeedConfig(seed=...)`
fully determines every row, so demo data and test fixtures are reproducible and
diffable. It bulk-inserts in chunks to keep the 365-day cohort fast. A test
asserts that the same seed yields byte-identical activity rows.

## Consequences

- **Positive:** typed models, deterministic migrations (`alembic check` is a
  drift gate in CI), fast isolated tests with no shared DB, reproducible seeds.
- **Positive:** the domain has no ORM dependency; swapping storage later is a
  matter of new mappers/repositories.
- **Negative:** two representations (entity and ORM model) to keep in sync;
  the mapper is where mistakes can hide, hence the protocol conformance tests.
- **Negative:** testcontainers needs a container engine; integration tests are
  therefore separated from the default fast unit run.

## Alternatives considered

- **Sync SQLAlchemy** — simpler, but mismatched with the async API.
- **Native Postgres enums** — stronger typing, but painful to evolve and
  invisible to `alembic check`.
- **ORM entities as the domain** — less code now, but couples the domain to
  persistence and blocks pure TDD in phase 5.
- **SQLite for tests** — fast, but diverges from PostgreSQL (types, JSONB,
  constraints) and would give false confidence.
- **Repository over a generic UoW/application layer** — deferred; YAGNI until
  there is behaviour to coordinate.
